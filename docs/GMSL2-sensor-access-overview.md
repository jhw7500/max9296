# GMSL2 카메라 시스템에서 센서 레지스터 접근 방식

## 시스템 전체 구조

차량용 카메라 시스템에서는 SoC(프로세서)와 이미지 센서 사이에 여러 칩이 직렬로 연결된다.

```
┌──────────┐    I2C     ┌──────────┐   GMSL2    ┌──────────┐    I2C     ┌──────────┐    I2C     ┌──────────┐
│  iMX8MP  │ ────────── │ MAX9296  │ ═══════════ │ MAX9295  │ ────────── │  AP1302  │ ────────── │  AR0234  │
│  (SoC)   │            │ (역직렬) │   고속링크   │ (직렬)   │            │  (ISP)   │            │ (센서)   │
└──────────┘            └──────────┘            └──────────┘            └──────────┘            └──────────┘
  프로세서               수신기                  송신기                  영상처리                 카메라
```

### 각 칩의 역할

| 칩 | 역할 | 비유 |
|----|------|------|
| **iMX8MP** | 메인 프로세서. 카메라 데이터를 최종 소비 | 본사 |
| **MAX9296** | GMSL2 역직렬화기(Deserializer). 고속 직렬 데이터를 원래 형태로 복원 | 본사 쪽 수신 장비 |
| **MAX9295** | GMSL2 직렬화기(Serializer). 카메라 데이터를 고속 직렬 신호로 변환 | 현장 쪽 송신 장비 |
| **AP1302** | ISP(Image Signal Processor). 센서의 RAW 이미지를 처리(노출, 색상 보정 등) | 현장 관리자 |
| **AR0234** | 이미지 센서. 빛을 전기 신호로 변환 | 카메라 눈 |

### GMSL2란?

GMSL2(Gigabit Multimedia Serial Link 2)는 Maxim(현 ADI)의 차량용 고속 직렬 통신 규격이다.

- 동축 케이블 **1가닥**으로 영상 데이터 + I2C 제어 신호를 동시에 전송
- 최대 15m 거리, 6Gbps 대역폭
- **I2C 터널링**: SoC에서 I2C 명령을 보내면 GMSL2 링크를 통해 원격지 칩에 도달

SoC 입장에서는 일반 I2C처럼 보이지만, 실제로는 GMSL2 링크를 거쳐 원격지 칩에 도달한다.

## 문제: SoC에서 센서를 직접 제어할 수 없다

AR0234 센서는 AP1302 ISP 뒤에 있어 SoC가 직접 접근할 수 없다.

```
SoC ──I2C──> MAX9296 ══GMSL2══> MAX9295 ──I2C──> AP1302 ──I2C──> AR0234
                                                    ↑
                                              여기까지만 직접 접근 가능
```

AR0234에 접근하려면 AP1302를 경유해야 하며, AP1302가 제공하는 경유 방법이 2가지: **SIPM**과 **DMA**이다.

---

## 방법 1: SIPM (Sensor Interface Pass-through Mode)

AP1302 내부에 "I2C 대리인"이 있다고 생각하면 된다. SoC가 SIPM 레지스터에 요청을 적으면 AP1302가 대신 센서에 I2C 트랜잭션을 수행하고 결과를 돌려준다.

```
[SoC 요청]                           [AP1302 내부]                    [센서]
                                    ┌─────────────────┐
"0x3000 읽어줘" ──I2C(GMSL경유)──>  │ SIPM 레지스터    │
                                    │  CTL = 읽기모드  │ ──I2C──> AR0234
                                    │  ADR = 0x3000   │          R0x3000
                                    │  GO  = 시작!    │ <──────  결과
                                    │  DW  = 결과저장  │
"결과 읽기" <──I2C(GMSL경유)──────  │                 │
                                    └─────────────────┘
```

### 문제: AP1302 펌웨어와의 충돌

AP1302 FW도 센서 상태를 모니터링하기 위해 같은 SIPM을 사용한다. SoC가 주소를 적어놓아도 FW가 자기 주소로 덮어쓰는 경쟁 조건이 발생한다.

```
SoC:       ADR에 0x3000 쓰기 ─────┐
AP1302 FW: ADR에 0x0020 덮어쓰기 ─┐  ← FW가 자기 할 일을 함
SoC:       GO = 1 (시작!) ────────┘
결과:      0x0020의 값이 읽힘      ← SoC가 원한 0x3000이 아님
```

| 동작 | 결과 |
|------|------|
| 쓰기 | 정상 (FW가 쓰기 데이터를 덮어쓰지 않음) |
| **읽기** | **불안정** (FW가 주소를 덮어씀) |

---

## 방법 2: DMA (Direct Memory Access)

AP1302 내부에 SIPM과는 별도의 DMA 엔진이 있다. FW와 독립적으로 동작하므로 경쟁 조건이 없다.

```
[SoC 요청]                           [AP1302 내부]                    [센서]
                                    ┌─────────────────┐
"0x3000 읽어줘" ──I2C(GMSL경유)──>  │ DMA 엔진        │
                                    │  SRC = 센서정보  │ ──I2C──> AR0234
                                    │  DST = 결과주소  │          R0x3000
                                    │  CTRL = 시작!   │ <──────  결과
                                    │                 │
"결과 읽기" <──I2C(GMSL경유)──────  │  DST에서 추출   │
                                    └─────────────────┘
                                           ↑
                                    FW의 SIPM 사용과 완전 분리
```

### DMA 레지스터

| 주소 | 이름 | 역할 |
|------|------|------|
| 0x604A | SENSOR_SIP | 센서 정보 (sensor_id, 주소/데이터 크기 플래그) |
| 0x60A0 | DMA_SRC | 소스 (읽기: 센서 인코딩 / 쓰기: 데이터) |
| 0x60A4 | DMA_DST | 목적지 (읽기: 결과 저장 / 쓰기: 센서 인코딩) |
| 0x60A8 | DMA_SIZE | 전송 바이트 수 |
| 0x60AC | DMA_CTRL | 트리거 및 방향 제어 |

### 읽기/쓰기 구별: DMA_CTRL

AP1302 DMA 엔진은 `DMA_CTRL` 값으로 읽기/쓰기를 구별한다.

| DMA_CTRL | 방향 | 의미 |
|----------|------|------|
| **0x0032** | 센서 → AP1302 | 읽기 |
| **0x0302** | AP1302 → 센서 | 쓰기 |

CTRL 값에 따라 SRC/DST 역할이 바뀐다:
- 읽기: SRC=센서(소스), DST=AP1302 내부(목적지)
- 쓰기: SRC=AP1302 내부(소스), DST=센서(목적지)

### 인코딩

#### 선행 정보: SENSOR_SIP

DMA 전에 AP1302에서 센서 정보를 읽는다.

```
SENSOR_SIP (16-bit):
  bit[6:1]  = sensor_id   (센서 고유 ID, AP1302 FW가 부여)
  bit[8]    = addr_16     (1 = 레지스터 주소가 16비트)
  bit[9]    = data_16     (1 = 데이터가 16비트)
```

#### 센서 주소 인코딩 (SRC 또는 DST에 사용)

```
┌──────────────────────────────────────────────────┐
│ 31  26│25│24│23    17│16                        0│
│  port │d │a │sensor │     reg_addr               │
│       │16│16│  _id  │                             │
└──────────────────────────────────────────────────┘
```

#### 읽기 예시: AR0234 chip ID (0x3000) 읽기

```
DMA_SRC  = 센서 인코딩(reg=0x3000)      ← "어디서 읽을지"
DMA_DST  = 0x000060A4                    ← 결과 저장할 AP1302 내부 주소 (고정)
DMA_SIZE = 2
DMA_CTRL = 0x0032                        ← 읽기 트리거

완료 후 DMA_DST 재읽기 → 0x0A560000
디코딩: 0x0A560000 >> 16 = 0x0A56       ← chip ID
```

#### 쓰기 예시: test pattern ON (reg=0x3070, val=0x0001)

```
DMA_SRC  = (0x0001 << 16) | 0x000060A0  ← "무슨 데이터를" (상위=데이터, 하위=내부주소)
DMA_DST  = 센서 인코딩(reg=0x3070)      ← "어디에 쓸지"
DMA_SIZE = 2
DMA_CTRL = 0x0302                        ← 쓰기 트리거

(쓰기는 결과를 돌려받지 않으므로 디코딩 불필요)
```

#### 디코딩

읽기에서만 필요하며, DMA_DST를 재읽기하여 상위 비트에서 값을 추출하는 시프트 연산이다.

```
val = raw >> (32 - data_size_bytes * 8)
```

상위 비트에 결과가 오는 이유는 AP1302 DMA 엔진이 빅엔디안으로 데이터를 배치하기 때문이다.

## 비교 요약

| 항목 | SIPM | DMA |
|------|------|-----|
| 쓰기 | 정상 | 정상 |
| **읽기** | **불안정** (FW 경쟁) | **안정** |
| FW 간섭 | 있음 (같은 채널 공유) | 없음 (독립 엔진) |
| 구현 복잡도 | 단순 | 중간 (인코딩 필요) |
| 현재 드라이버 | 제거됨 | 사용 중 |
