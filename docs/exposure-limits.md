# 노출 시간 상·하한 — 실측과 측정법

**작성일**: 2026-09-19
**대상**: i.MX8MP + MAX9296 + MAX9295 + AP1302 + AR0234 (pim-camera-v016)
**검증 방식**: 보드 실측 (AP1302 DMA 경유 AR0234 raw register read, 스트리밍 중)

---

## 1. 결론

기본 AE 설정에서 `exp_time` 이 실제로 센서에 도달하는 범위는 양쪽이 막혀 있다.

```
    2행                                        min(프레임 주기, 0x2028)
  ◄──┤━━━━━━━━━━━━ 라인타임 단위로 선형 반영 ━━━━━━━━━━━━┤──►
 요청 무시                                          요청 무시
```

- **하한 = 센서 `COARSE_INTEGRATION_TIME` 최소 2행.** fps 와 무관하고 모드의 라인타임에만 비례한다.
- **상한 = `min(SENSOR_TOTAL_FRAME_TIME, AP1302 0x2028)`.** `0x2028`(PREVIEW_AE_MAX_ET)의 펌웨어
  기본값이 33,333 µs 라, **30 FPS 이하에서는 프레임 주기가 아무리 길어도 33.3 ms 를 넘지 못한다.**
- **양쪽 모두 에러 없이 조용히 잘린다.** 요청값은 `0x500c` 에 그대로 남아 `--get-ctrl` 로도
  dmesg 로도 드러나지 않는다. 실효 노출을 보려면 센서 레지스터를 직접 읽어야 한다(§4).
- `0x2028` 은 런타임에 조정할 수 있고(§3), v6.x 드라이버부터 `preview_ae_max_et` V4L2 컨트롤로
  노출돼 있다.

---

## 2. 실측값

전부 dual-wide, 스트리밍 중, `0x2028` = 펌웨어 기본값 33,333 µs 상태다.

### 2.1 상한

| 모드 | fps | 프레임 주기 | 라인타임 | 상한 실측 | 행 수 | 규칙값 |
|---|---:|---:|---:|---:|---:|---:|
| 3840x1080 | 15 | 66,667 µs | 26.267 µs | **33,374 µs** | 1268 | 33,333 |
| 2560x720 | 15 | 66,667 µs | 11.867 µs | **33,311 µs** | 2807 | 33,333 |
| 2560x720 | 30 | 33,333 µs | 11.867 µs | **33,014 µs** | 2782 | 33,333 |
| 2560x720 | 60 | 16,667 µs | 11.867 µs | **16,519 µs** | 1392 | 16,667 |
| 1280x360 | 15 | 66,667 µs | 6.81 µs | **33,362 µs** | 4899 | 33,333 |
| 1280x360 | 30 | 33,333 µs | 6.81 µs | **33,063 µs** | 4855 | 33,333 |
| 1280x360 | 60 | 16,667 µs | 6.81 µs | **16,562 µs** | 2432 | 16,667 |

"규칙값" 은 `min(프레임 주기, 33,333)` 이다. 일곱 조건 모두 실측이 규칙값의 99% 이상이다.
해상도는 상한에 영향을 주지 않는다 — 9배 차이나는 1080p@15 와 360p@15 가 33.37 / 33.36 ms 로
사실상 같다. 바뀌는 것은 같은 시간을 채우는 **행 수**뿐이다.

### 2.2 하한

| 모드 | 라인타임 | 하한 | 근거 |
|---|---:|---:|---|
| 3840x1080 | 26.32 µs | **52.6 µs** (2행) | 실측 — 70µs→2행, 50µs 부터 2행 고정, 1µs 도 2행 |
| 1280x360 | 6.81 µs | **13.6 µs** (2행) | 실측 — fps 15/30/60 에서 표가 완전히 동일 |
| 2560x720 | 11.8667 µs | **23.7 µs** (2행) | 실측 — 24µs→2행(정상 내림), 20µs 부터 2행 고정 |

`FINE_INTEGRATION_TIME`(R0x3014)은 모든 조건에서 `10` 고정이라 미세 보정에도 관여하지 않는다.
양자화는 라인타임 단위 **내림**이다(예: 360p 에서 100µs → 14행, 기대 14.68).

**fps 와 무관하다는 것이 하한의 핵심 성질이다.** 360p 에서 fps 를 4배 바꿔도 하한 행 수는 2로
동일했다. 상한이 fps 를 따라가는 것과 방향이 반대다.

## 3. `0x2028` 조절로 상한 올리기

`0x2028`(PREVIEW_AE_MAX_ET, µs, 32비트)은 preview 컨텍스트의 AE 노출 상한이다. 값을 바꾸면
**스트리밍 중 무중단으로** 상한이 따라 움직인다.

### 3.1 양방향 실측

| 모드 | fps | `0x2028` | `exp_time` 요청 | 실효 노출 | 행 수 |
|---|---:|---:|---:|---:|---:|
| 3840x1080 | 15 | 33,333 | 60,000 | 33,307 µs | 1268 |
| 3840x1080 | 15 | **60,000** | 60,000 | **59,968 µs** | 2283 |
| 2560x720 | 15 | 33,333 | 40,000 | 33,311 µs | 2807 |
| 2560x720 | 15 | **60,000** | 40,000 | **39,980 µs** | 3369 |
| 2560x720 | 15 | **60,000** | 55,000 | **54,980 µs** | 4633 |
| 2560x720 | 60 | 33,333 | 16,000 | 15,997 µs | 1348 |
| 2560x720 | 60 | **8,000** | 16,000 | **7,986 µs** | 673 |

올리는 방향과 내리는 방향 모두 상한이 따라간다. fps=60 에서는 프레임 주기(16,667)가 이미
33,333 보다 작아 올려도 효과가 없으므로, **낮추는 방향**으로 검증했다.

### 3.2 AE 모드와 무관하다

AP1302 데이터시트는 `PREVIEW_AE_MAX_ET` 를 "AE 알고리즘이 결정한 노출" 의 한계로 기술하지만,
이 펌웨어는 **`AE_MANUAL_EXP_TIME`(0x500c) 경로에도 동일하게 적용**한다. 2560x720@15fps,
`exp_time=60,000` 요청, 매 측정마다 `0x5002` readback 으로 모드를 확인한 결과:

| `AE_CTRL`(0x5002) | 의미 | `0x2028`=33,333 | `0x2028`=60,000 |
|---|---|---:|---:|
| `0x0290` | MANUAL (드라이버 `ae_on=0`) | 2807행 / 33,311 µs | **5054행 / 59,976 µs** |
| `0x0299` | AUTO (드라이버 `ae_on=1`) | 2807행 | **5054행** |
| `0x000c` | full-auto (펌웨어 기본) | 2807행 | **5054행** |

세 모드가 완전히 동일하다. 데이터시트 서술만 믿고 "manual 에서는 무효" 로 판단하면 틀린다.

### 3.3 `0x2024` 는 무관하다

인접한 `0x2024`(PREVIEW_AE_UPPER_ET)는 같은 기본값 33,333 을 갖지만 상한에 기여하지 않는다.
2560x720@15fps, `exp_time=40,000` 기준:

| 조건 | 결과 |
|---|---:|
| 기준 (둘 다 33,333) | 2807행 |
| `0x2024` = 60,000 **단독** | 2807행 — 변화 없음 |
| `0x2028` = 60,000 **단독** | 3369행 |
| 둘 다 60,000 | 3369행 — `0x2028` 단독과 동일 |

`0x2024` 가 구속했다면 마지막 두 행이 달라야 한다. `0x202c`(PREVIEW_SS, 실측 66,125,825)도 무관.

### 3.4 실용 한계

상한을 프레임 주기 가까이 올리면 노출은 늘지 않고 **fps 만 무너진다.** 3840x1080@15fps 에서
`0x2028` 을 기본값으로 둔 채 요청값만 올렸을 때:

| `exp_time` | 행 수 | ISI irq/s |
|---:|---:|---:|
| 10,000 ~ 25,000 | 380 ~ 951 | 15 |
| 33,000 | 1255 | 12 |
| 40,000 | 1268 (포화) | 10 |
| 60,000 | 1268 (포화) | **7** |

노출은 1268행에 고정인데 fps 가 단조 감소한다. AP1302 가 요청값 기준으로 트리거 주기를 늘리지만
센서 노출은 상한에서 잘리기 때문으로 **추정**한다(미확인). **실용 상한은 프레임 주기의 90% 정도**다.

## 4. 측정법

### 4.1 무엇을 읽는가

| 대상 | 레지스터 | 의미 |
|---|---|---|
| **실효 노출** | AR0234 `R0x3012` COARSE_INTEGRATION_TIME | **행 수**. 이것만이 실제 적용값이다 |
| 라인타임 | AP1302 `0x00d8` SENSOR_LINE_TIME | u16.16 µs. 행 → 시간 환산에 필요 |
| 프레임 시간 | AP1302 `0x00fc` SENSOR_TOTAL_FRAME_TIME | 블랭킹 포함 |
| 요청값 | AP1302 `0x500c` EXP_TIME | 드라이버가 쓴 값(잘리기 전) |
| 상한 | AP1302 `0x2028` PREVIEW_AE_MAX_ET | µs, 32비트 |
| AE 모드 | AP1302 `0x5002` AE_CTRL | `0x0290` manual / `0x0299` auto / `0x000c` full-auto |

**`R0x3164`(AE_COARSE_INTEGRATION_TIME, RO)는 쓰지 마라.** 데이터시트는 "현재 프레임의 적분
시간" 이라고 하지만 모든 조건에서 `0x0001` 고정이다. AP1302 가 센서 내장 AE 를 쓰지 않고
`R0x3012` 를 직접 제어하기 때문으로 보인다.

### 4.2 절차

```bash
# 0) 보드 점유 (공유 자원)
set -a; . ~/.config/jhw-control/control.env; set +a
"$HOME/.local/bin/jhw-control-host" board with pim --mode exclusive --for 30m \
    --session <id> --purpose "노출 상하한 측정" -- <측정 스크립트>

# 1) 스트리밍 상태 확보 — gstApp 운영 상태를 쓰거나, 직접 협상한다
cat /sys/bus/i2c/devices/2-0048/prepare     # state=CONSUMED 여야 한다

# 2) 라인타임 확인 (u16.16)
/opt/pim/bin/i2cread.sh 2 0x11 0x00d8 4      # 예: 0x001a4444 -> 26.267us

# 3) 노출 설정 후 실효값 읽기
v4l2-ctl -d /dev/v4l-subdev2 -c exp_time=20000
/opt/pim/bin/cam_ap1302_dma_verify.sh 0 0x3012   # read-before 의 value=
# 실효 노출 = 행 수 x 라인타임
```

모드를 직접 협상하려면(gstApp 없이):

```bash
systemctl stop cam-operate.service; pkill -9 -x gstApp
bash /root/camtest/cam_hard_reset.sh -q
printf '1 %s 1280 360 30 3\n' "$(date +%s%N)" > /sys/bus/i2c/devices/2-0048/prepare
v4l2-ctl -d /dev/video4 --set-fmt-video=width=1280,height=360,pixelformat=UYVY
setsid nohup v4l2-ctl -d /dev/video4 --stream-mmap --stream-count=100000 \
    --stream-to=/dev/null </dev/null >/tmp/stream.log 2>&1 &
```

`prepare` 쓰기 형식은 `1 <generation> <width> <height> <fps> <enable>` 이다
(→ [`parallel-prepare-v1.md`](parallel-prepare-v1.md)).

### 4.3 함정

- **스트리밍이 없으면 `exp_time` 이 센서에 반영되지 않는다.** `prepare` 가 `READY` 인 상태에서
  스윕하면 COARSE 가 초기값에 고정된 채 전 구간 무반응이다. 반드시 `CONSUMED` 까지 갈 것.
- **1080p(3840x1080) 를 `v4l2-ctl --stream-mmap` 으로 받지 마라.** UYVY 250 MB/s 로 4코어 A53 이
  마비되고 ssh 가 exit 255 로 끊긴다. fps 대조는 **360p(1280x360, 최대 120fps)** 로 한다.
- **`i2cread.sh` 출력은 `0x..` hex 바이트열이다.** awk 로 조립하면 `"0x00"` 이 0 으로 읽혀 전부
  0 이 나온다. bash 산술 `v=$(( (v<<8)|b ))` 을 쓸 것(`cam_ap1302_dma_verify.sh` 와 같은 방식).
- **듀얼에서 쌍의 노출이 갈리면 CSI2 가 붕괴하고 ISI 가 0 이 된다**(이슈 #64). 스윕은 공용
  `exp_time` 으로 쌍을 동시에 움직이고, `0x2028` 도 `0x11`/`0x12` 양쪽에 같은 값을 쓴다.
- **`pkill -f` / `pgrep -f` 는 자기 명령줄에 매칭된다.** ssh 원격 실행에서 자기 셸을 죽여 세션이
  끊긴다. `pkill -9 -x <comm>` 을 쓸 것.
- 보드 python 은 3.8, 개발 머신은 3.10 이다.

## 5. 드라이버 인터페이스

v6.x 부터 `0x2028` 을 V4L2 컨트롤로 조정할 수 있다.

```bash
v4l2-ctl -d /dev/v4l-subdev2 -c preview_ae_max_et=60000
v4l2-ctl -d /dev/v4l-subdev3 -c preview_ae_max_et=60000   # 4채널이면 양쪽 subdev 에
```

- 디저라이저 단위 컨트롤이다. 4채널 보드는 subdev 두 개에 각각 써야 한다.
- 값을 클램프하지 않는다(조사용). 프레임 주기를 넘으면 기존 `over_period` 경고와 같은 형식으로
  `preview_ae_max_et above frame period ... over_period=1 action=write` 를 남긴다.
- 듀얼에서는 `0x11`/`0x12` 양쪽에 같은 값이 나간다.
- 캐시되고 펌웨어 리로드 후 replay 되지만, **앱 재기동 시에는 edgeconf JSON 이 정본**이다
  (캐시가 모듈과 함께 사라진다). 실측으로 확인: 60,000 설정 후 재기동하면 레지스터·컨트롤 모두
  33,333 으로 복귀한다.

상세는 [`../V4L2_CTRL_GUIDE.md`](../V4L2_CTRL_GUIDE.md) §3.1, §3.3.

## 6. 운영상 함의

- **설정값과 실효값이 다를 수 있다.** 측정 시점에 ch2/ch3 가 `exp_time=50,000` 으로 운영되고
  있었는데 실효는 33,374 µs 로 잘리고 있었다. 의도한 노출이 50 ms 였다면 달성되지 않은 것이다.
- **저조도 대응으로 fps 를 낮추는 것은 효과가 없다.** 30 FPS 이하에서는 상한이 33.3 ms 로 고정
  이므로 15 FPS 로 내려도 노출을 더 줄 수 없다. `0x2028` 을 올려야 한다.
- **`0x2028` 은 cold init 마다 33,333 으로 복귀**한다. 드라이버가 캐시를 replay 하지만 모듈이
  재로드되면 사라진다. 상시 적용이 필요하면 edgeconf/앱 쪽에서 매번 설정해야 한다.
