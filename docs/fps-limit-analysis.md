# 프레임레이트 상한 분석 — FHD 60fps 가 안 되는 이유

**작성일**: 2026-08-11
**대상 시스템**: i.MX8MP + MAX9296 + MAX9295 + AP1302 + AR0234 (pim-camera-v016)
**검증 방식**: 보드 실측 (하드웨어 인터럽트 카운터, AP1302/MAX9296 레지스터 직접 read/write, 드라이버 재빌드, 펌웨어 blob 패치)

---

## 1. 결론

**AP1302 의 1080p 모드가 센서 판독과 출력 대역 양쪽 모두 30fps 급으로 설정돼 있다.** 관문이 두 개이고 둘 다 넘어야 한다.

### (가) 센서 판독 시간 — 한 프레임을 트리거 주기 안에 못 읽는다

```
1080p 모드 라인타임 26.27 µs × 1080 라인 = SENSOR_FRAME_TIME 28,368 µs
                        60fps 트리거 주기 = 16,667 µs      ← 초과
  → 센서가 한 주기 안에 프레임을 못 냄. 트리거 배수(2배·3배)로 떨어져 19.8~21.8 fps
```

이 값은 `PREVIEW_LINE_TIME`(R0x201C) 으로 **런타임에 바꿀 수 있다.** 13.0 µs 를 쓰면 `SENSOR_FRAME_TIME` 이 실제로 **14,063 µs** 로 내려간다 (보드 실측). AR0234 는 60fps 급 타이밍이 가능하다.

### (나) 출력 대역 — 초당 비트를 못 내보낸다

```
AP1302 MIPI 출력 = 300 Mbps/lane × 4 lane = 1.2 Gbps

  이론 상한:  FHD 1.2e9 / (1920×1080×16bpp) = 36.2 fps
             HD  1.2e9 / (1280×720×16bpp)  = 81.4 fps
  실측:       FHD 28.3 fps (이론의 78%)
             HD  55.5 fps (이론의 68%)

  FHD60 필요 = 1920×1080×16×60 = 1,990 Mbps  →  1.2 Gbps 의 166%, 초과
```

이 값의 출처는 펌웨어 blob `v4l-ap1302-ar0234.fw` 의 **오프셋 0x11 한 바이트**다.

```
00000010: 012c 0000 ...      0x012c0000 = 300.0  (u16.16, big-endian)
            ^^
```

`0x2c` → `0xf4` 로 바꾸면 `HINF_MIPI_FREQ` 가 **300.0 → 499.2 Mbps** 로 실제 변한다 (보드 실측). AP1302 는 패치된 blob 을 오류 없이 받아들이고(`R0x0006 ERROR = 0x0000`), 펌웨어는 이 값에 반응해 센서 라인타임까지 **26.27 → 15.96 µs 로 스스로 재계산**한다. 즉 이 바이트는 무시되지 않고 클럭 트리 계산에 실제로 쓰인다.

**다만 그렇게 만든 설정은 동작하지 않는다.** 패치본을 적재하면 AP1302 의 출력 프레임 수(`R0x0002` HINF_FRAME_CNT)가 **0** 이 된다 — 30fps 도 20fps 도 아닌 완전한 0 이다. 하류(MAX9296·SoC)가 못 받는 것이 아니라 **소스 자체가 아무것도 내보내지 않는다.** blob 안의 클럭 값들이 서로 정합해야 하는데 하나만 바꿔 불일치를 만든 것으로 보인다(PLL·분주비 등 동반 값 미조정).

따라서 **1바이트 패치는 "대역을 올릴 수 있다"는 증명이 아니라, "이 바이트가 대역을 정한다"는 증명까지만이다.** §7 참조.

### 두 관문의 관계

기본 설정에서 (가)는 ~30 fps, (나)는 ~28 fps 로 **거의 같은 지점에서 동시에 걸린다.** 벤더가 1080p 를 30fps 모드로 일관되게 설계한 결과다.

- (가)만 해결한 상태의 최고치 = **26.7 fps** — (나)의 실효 상한(~28)과 일치
- (나)만 해결하면 센서가 프레임을 제때 못 내므로 무의미

**따라서 "ISP 레지스터는 해당 없고 펌웨어만 문제"가 아니다.** ISP 쪽 `PREVIEW_LINE_TIME` / `PREVIEW_MAX_FPS` / `TRIGGER_MAX_MISMATCH` 는 모두 필요하고, 셋 다 드라이버가 런타임에 쓸 수 있다. 전체 변경 목록은 §7.

### 칩 한계는 아니다

AP1302 데이터시트 스펙은 **450 Mpixel/s, 1080p@120fps, MIPI 4 lane × 1.2 Gbps/lane** 이고, FHD60 에 필요한 124.4 Mpixel/s 는 그 28% 다. 현재 설정이 스펙의 1/4 로 묶여 있을 뿐이다.

### 남은 난관

**(나)를 여는 방법을 아직 찾지 못했다.** 1바이트 패치로 `HINF_MIPI_FREQ` 를 499.2 Mbps 로 바꾸면 펌웨어가 라인타임까지 재계산하지만, 그 설정에서 **ISP 출력이 0 이 된다**(SERDES 상류 `R0x0002` 로 직접 확인). 하류가 못 받는 것이 아니라 소스가 죽는다 — blob 안의 동반 클럭 값(PLL·분주비)이 함께 맞춰져야 하는데 그 값들을 확인하지 못했다.

따라서 하류 정합(MAX9296 `0x0320`, SoC `csis-hs-settle`)은 **시험 자체를 못 한 상태**다. 상류가 살아야 도달할 수 있다.

**정합한 펌웨어를 벤더에서 받는 것이 사실상 전제조건이다** (§7.5 에 문의 근거 정리).

## 2. 시스템 경로와 측정점

```text
AR0234 ──> AP1302 ──MIPI──> MAX9295 ══GMSL2══> MAX9296 ──MIPI CSI-2──> i.MX8MP
 센서        ISP              직렬화        3Gbps      역직렬화            ISI ──> v4l2
             │                                            │                │
             │                                            │                │
      [측정] R0x0002                                 [측정] /proc/interrupts
      HINF_FRAME_CNT                            32e50000.csi / 32e02000.isi
      = AP1302 가 실제 내보낸 프레임 수          = SoC 가 실제 받은 프레임 수
```

병목 위치를 가르는 핵심은 **SERDES 상류와 하류를 동시에 세는 것**이다.

| 측정점 | 레지스터 / 소스 | 의미 |
|---|---|---|
| AP1302 출력 | `R0x0002 FRAME_CNT[15:8]` (HINF_FRAME_CNT) | 8비트 순환. 2초 간격이면 60fps 에서도 120프레임이라 안전 |
| SoC CSI-2 수신 | `/proc/interrupts` `32e50000.csi` | 프레임당 2회 (Frame Start + Frame End) — 실측 확인 |
| ISI 기록 | `/proc/interrupts` `32e02000.isi` | 프레임당 1회 |

채널 매핑:

| video 노드 | ISI | CSI-2 | 디시리얼라이저 | 채널 |
|---|---|---|---|---|
| `/dev/video3` | `32e00000.isi` | `32e40000.csi` | `max9296 1-0048` (i2c1) | ch2 / ch3 |
| `/dev/video4` | `32e02000.isi` | `32e50000.csi` | `max9296 2-0048` (i2c2) | ch0 / ch1 |

드라이버 모드 대응 (`max9296.c:731-764`):

| 해상도 | 모드 | 레지스터 테이블 |
|---|---|---|
| 1920×1080 | `MAX9296_MODE_1920x1080` | `max9296_init_setting_720p_30fps_L` (**단일채널**) |
| 3840×1080 | `MAX9296_MODE_3840x1080` | `max9296_init_setting_1080p_crop_720p_2ch_30fps` (**듀얼**) |

## 3. 실측 데이터

### 3.1 해상도 × 요청 fps

하드 리셋 후 **첫 스트림**, 펌웨어 기본값, 레지스터 조작 없음. `/dev/video4` 단일채널.

| 요청 fps | 1280×720 | Mpix/s | 1920×1080 | Mpix/s |
|---|---|---|---|---|
| 30 | **29.84** | 27.5 | **28.33** | **58.8** |
| 40 | 33.97 | 31.3 | 19.89 | 41.2 |
| 50 | **47.52** | 43.8 | 21.82 | 45.3 |
| 60 | **54.03** | 49.8 | 19.84 | 41.1 |

- FHD 는 30 초과를 요청하면 **오히려 나빠진다** (40 요청 → 40/2 = 19.9, 60 요청 → 60/3 = 19.8). 정수 분주다.
- HD 40fps 만 비단조 (50·60 보다 낮음). 원인 미규명. 실용상 40 대신 50 을 쓰면 된다.
- `v4l2-ctl` 측정치는 초기 램프를 포함해 정상상태보다 2~3fps 낮다. gstApp 구동 중 정상상태 실측은 FHD30 에서 **29.6 fps**.

### 3.2 채널 구성 4가지

| 케이스 | 구성 | @30fps | @60fps |
|---|---|---|---|
| A | ch0+ch1 듀얼 (video4, 3840×1080) | 27.33 | **0** |
| B | ch2+ch3 듀얼 (video3, 3840×1080) | 27.33 | 19.80 |
| C | ch0+ch3 동시 (video4+video3, 각 1920×1080) | 26.73 / 26.63 | 19.81 / 19.81 |
| D | 단일 1채널 (video4, 1920×1080) | 27.67 | 19.80 |

**채널 수를 줄여도 FHD60 은 안 된다.** 병목이 공유 자원이 아니라 카메라 모듈 내부(각 카메라가 자기 AP1302 와 자기 GMSL 링크를 가짐)이기 때문이다.

케이스 A(ch0/ch1 듀얼 @60)만 0 프레임이다. 30fps 에서는 A·B 가 동일한데 60fps 에서만 갈린다. **ch0/ch1 은 ISI 1, ch2/ch3 은 ISI 0 을 쓰고 두 ISI 는 대칭이 아니다** — §6.2 참조.

### 3.3 AP1302 내부 클럭 (실측, u16.16)

FHD 스트림 중 `/dev/video4` 기준.

| 레지스터 | 원시값 | 실제 |
|---|---|---|
| `R0x0054` CPU_FREQ | `0x00f9999a` | 249.6 MHz |
| `R0x0058` IPIPE_FREQ | `0x00e2e8ba` | 226.9 MHz |
| `R0x005C` SINF_FREQ | `0x02580000` | 600.0 MHz |
| `R0x0060` HINF_FREQ | `0x004b0000` | 75.0 MHz |
| **`R0x0068` HINF_MIPI_FREQ** | **`0x012c0000`** | **300.0 Mbps** |
| `R0x0074` SENSOR_INPUT_FREQ | `0x00180000` | 24.0 MHz |
| `R0x0078` SENSOR_PIXEL_FREQ | `0x005a0000` | 90.0 MHz |
| `R0x6024` SYSTEM_FREQ_IN | `0x00300000` | 48.0 MHz |
| `R0x602C` PLL_0_DIV | `0x00280300` | FB_DIV 40 / REF_DIV 3 / OUT_DIV 0 |
| `R0x6038` PLL_1_DIV | `0x00280300` | 동일 |

PLL 검산: `fref = 48/(3+1) = 12 MHz` → `fvco = 12 × 40 × 2 = 960 MHz` (규정 800~1600 만족)

`IPIPE_FREQ = 226.9 MHz` 이므로 **처리 능력은 충분하다.** 병목은 처리가 아니라 출력 링크다.

### 3.4 센서 타이밍 (실측)

| 조건 | SENSOR_LINE_TIME | SENSOR_FRAME_TIME | SENSOR_TOTAL_FRAME_TIME |
|---|---|---|---|
| 1920×1080 기본 | 26.27 µs | 28,368 µs | 33,4xx µs |
| 1280×720 기본 | 14.80 µs | — | 15,969 µs |
| 1920×1080, `PREVIEW_LINE_TIME` 강제 13.0µs | 13.02 µs | 14,063 µs | 16,684 µs |

**펌웨어는 해상도 모드별로 다른 센서 타이밍을 쓴다.** 720p 모드는 60fps 급(14.80µs), 1080p 모드는 30fps 급(26.27µs)이다.

그리고 `PREVIEW_LINE_TIME`(R0x201C) 으로 라인타임을 13µs 까지 낮추면 센서가 실제로 따라온다 — **AR0234 는 60fps 급 타이밍이 가능하다.** 다만 그래도 출력은 26.7fps 에서 멈춘다 (§5).

## 4. 관문 (나) 출력 대역 — 근거

이 절은 §1 의 두 관문 중 **(나) 출력 대역**에 대한 근거다. **(가) 센서 판독 시간**의 근거는 §3.4 (라인타임 26.27µs → `SENSOR_FRAME_TIME` 28,368µs, 그리고 `PREVIEW_LINE_TIME` 13.0µs 강제 시 14,063µs 로 실동작) 에 있다.

### 4.1 산술 정합

관측된 모든 fps 가 **단일 대역 상한 1.2 Gbps** 로 설명된다.

| 조건 | 실측 fps | 비트레이트 | 1.2 Gbps 대비 |
|---|---|---|---|
| HD @60 | 55.5 | 818 Mbps | 68% |
| FHD @30 | 28.3 | 939 Mbps | 78% |
| FHD @60 (필요) | — | 1,990 Mbps | **166%** |

MIPI 패킷 오버헤드와 블랭킹을 감안하면 실효 68~78% 는 타당한 범위다.

### 4.2 병목 위치 확정 — 상·하류 동시 측정

`1920×1080 @60fps` 요청 상태에서 2초 간격 5회:

| 구간 | AP1302 출력 (SERDES 상류) | SoC CSI2 수신 (하류) |
|---|---|---|
| 1회 | 20.0 fps (40 프레임) | 20.0 fps (40 프레임) |
| 2회 | 20.5 fps (41 프레임) | 20.0 fps (40 프레임) |
| 3회 | 20.0 fps (40 프레임) | 20.0 fps (40 프레임) |
| 4회 | 20.0 fps (40 프레임) | 20.0 fps (40 프레임) |
| 5회 | 20.5 fps (41 프레임) | 20.0 fps (40 프레임) |

**AP1302 가 내보낸 수와 SoC 가 받은 수가 일치한다.** GMSL 링크도 디시리얼라이저도 한 장도 버리지 않는다. 병목은 AP1302 출력 그 자체다.

역압(back-pressure) 가능성도 배제된다 — MAX9296 `0x0320 = 0x24` 기준 하류 용량은 1.6 Gbps 인데 실제 사용량은 20fps = 663 Mbps 로 41% 에 불과하다. 그리고 실측값이 요청의 정확한 정수 분주(60/3, 40/2)라는 점도 대역 포화가 아닌 트리거 동기 분주의 양상이다.

### 4.3 출처 확정 — 펌웨어 blob

**(가) 동작 증거**

드라이버가 `0x6034` 에 쓰는 값을 `0x012c0000`(300.0) → `0x01f40000`(500.0) 으로 바꿔 재빌드·배포했다.

```
로드된 모듈 srcversion = 5DD3E8A82EDC538874BE2CF   (신규, 500.0 을 씀)

펌웨어 로드 후 읽으면:
  R0x6034        = 0x012c0000   (300.0)  ← 드라이버가 쓴 500.0 이 아님
  HINF_MIPI_FREQ = 300.0 Mbps
```

드라이버 쓰기와 이 읽기 사이에 있는 것은 **펌웨어 blob 처리(`0x6002 = 0xffff`)뿐**이다. blob 이 이 값을 되돌린다.

**(나) 바이트 증거**

```
$ xxd -l 32 /lib/firmware/v4l-ap1302-ar0234.fw
00000000: 0500 001c 0000 0000 0000 0010 6035 0002  ............`5..
00000010: 012c 0000 6029 0002 0001 0000 0300 0810  .,..`)..........
          ^^^^^^^^^
          0x012c0000 = 300.0 (u16.16 BE), 레지스터 0x6034 참조 직후
```

**(다) 패치 검증**

오프셋 0x11 을 `0x2c` → `0xf4` 로 바꾸고 재로드:

```
HINF_MIPI = 499.2 Mbps   (기존 300.0)
HINF      = 124.8 MHz    (기존 75.0)
R0x6034   = 0x01f40000   (더 이상 덮어써지지 않음)
ERROR     = 0x0000       (AP1302 오류 없음, CRC 거부 없음)
라인타임   = 15.96 us     (기존 26.27 — 펌웨어가 새 대역에 맞춰 재계산)
로그: start_fw_load → end_fw_load → loaded v4l-ap1302-ar0234.fw firmware (81616 bytes)
```

드라이버의 펌웨어 로더(`max9296_load_firmware`, `max9296.c:3125~`)는 헤더 파싱도 CRC 검증도 하지 않고 81,616 바이트를 그대로 칩에 전송한다.

라인타임이 자동으로 바뀐 것은 **이 바이트가 무시되지 않고 클럭 트리 계산에 실제로 쓰인다**는 증거다.

**(라) 그러나 그 설정은 동작하지 않는다**

패치본 적재 상태에서 SERDES 상류 측정점(`R0x0002` HINF_FRAME_CNT)으로 ISP 출력을 직접 세면:

```
1920x1080 @60fps 요청, 패치본(499.2 Mbps) 적재

  HINF_MIPI = 499.2 Mbps | 라인 15.96 us | TOTAL 33,331 us -> 센서 30.0 fps
  ISP 출력  =  0 프레임 / 2.02s = 0.0 fps   (3회 반복 전부 0)
  ISI(하류) = 증가 없음
```

**센서는 30 fps 로 돌고 있는데 ISP 가 한 장도 내보내지 않는다.** 하류가 못 받는 것이 아니라 소스가 죽어 있다. 이 상태에서는 `PREVIEW_LINE_TIME` / `PREVIEW_MAX_FPS` / `TRIGGER_MAX_MISMATCH` 쓰기도 전혀 반영되지 않는다(라인타임이 15.96 에서 안 움직임).

blob 안의 클럭 값들이 서로 정합해야 하는데 하나만 바꿔 불일치를 만든 것으로 보인다. PLL·분주비 등 동반 값이 500 Mbps 에 맞춰져 있지 않다.

**따라서 이 패치가 증명하는 것은 "이 바이트가 MIPI 출력 대역을 정한다"까지이고, "대역을 올릴 수 있다"까지가 아니다.**

## 5. 배제된 원인 (전부 실측 근거)

| 후보 | 배제 근거 |
|---|---|
| **ISI 병목** | CSI2 프레임 301 = ISI 프레임 301, 손실 0. **단 fps 상한의 원인이 아니라는 뜻일 뿐이며, ISI 0/1 사이에는 구조적 비대칭이 실재한다 (§6.2)** |
| **GMSL / SERDES 대역폭** | AP1302 출력 20.0 fps = SoC 수신 20.0 fps (§4.2) |
| **센서 능력** | `PREVIEW_LINE_TIME` 13.02µs 강제 시 `SENSOR_FRAME_TIME` 14,063µs (=71fps) 실동작 |
| **노출 한계** | 노출 10ms vs 프레임 28ms. 5ms 로 줄여도 `SENSOR_FRAME_TIME` 불변 (28,368) |
| **플리커 감쇄** | `FLICK_CTRL`(R0x5440) 실측값 `0x0000` — 이 펌웨어에서 원래 비활성. 켜봐도 fps 불변 |
| **AP1302 칩 처리량** | 스펙 450 Mpixel/s, 1080p@120fps. 필요량 124.4 Mpixel/s 는 28% |
| **AP1302 오류** | `WARNING_0~3`, `ERROR` 가 정상 동작 케이스(720p@60)와 동일 |
| **SoC 수신부** | 4레인 / CSIS 500MHz. i.MX8MP 사양상 여유. 이전에 클럭을 266→500MHz 로 올렸으나 무효였던 것도 이 때문 |
| **`0x0471` 미복구** | 실패 상태에서 이미 `0x83`, 주입해도 변화 없음 |
| **`sensor->restart` 경로** | gstApp kill → 자동 재시작이 정상 동작 (restart 경로로 재시작하고 스트리밍 성공) |

### 부분적으로 유효했던 것

**트리거 프레임 스킵** — `TRIGGER_MAX_MISMATCH`(R0x6112, 기본 20µs) 를 0 으로 두면 FHD@60 이 19.8 → **26.7 fps**, HD@50 이 46.0 → **49.8 fps** 로 개선된다. 다만 FHD 는 그래도 30fps 설정보다 나쁘므로 실익이 없다.

## 6. 별도로 발견한 문제

### 6.1 파이프라인 물림

짧은 스트림을 즉시 재시작하면 파이프라인이 물려 **재부팅 전까지 프레임이 안 나오는** 상태가 된다. 이때:

- GMSL 링크는 `CTRL3 = 0xfa` **LOCKED**, 디시리얼라이저 CSI 출력도 `0x0313 = 0x86` **ON**
- CSI2 이벤트 카운터가 **에러까지 전부 0** → SoC D-PHY 가 락을 못 잡음
- `rmmod/modprobe max9296 + imx8-media-dev` 로는 **복구 안 됨** (cam_disable.sh 와 동일한 방식)
- `32e40000.csi` (mxc-mipi-csi2-sam) **만 unbind/bind 하면 복구됨**

원인: `mipi_csis_phy_reset()` 이 probe 와 runtime-PM resume 에서만 호출되고 `mipi_csis_start_stream()` 에는 없다 (`imx8-mipi-csi2-sam.c`).

검증 결과:

| 단계 | 결과 |
|---|---|
| 하드 리셋 후 첫 스트림 | 26.86 fps |
| 짧은 스트림 즉시 재시작 ×2 | 프레임 없음 (물림 재현) |
| **모듈 리셋만** | **프레임 없음** |
| **하드 리셋 (CSI2+ISI 리바인드)** | **27.38 fps** |

**단, 실제 gstApp 의 kill → 자동 재시작에서는 이 현상이 나타나지 않는다.** 재현 조건은 "2초 남짓의 짧은 스트림을 0.5초 안에 재시작"이며, 실제 앱은 스트림이 충분히 확립된 뒤 2초 이상 간격으로 재시작한다. 운용 중 발생하는 문제가 아니라 시험 절차상의 인위적 상황이다.

대응 도구: `tools/cam_hard_reset.sh` (§8)

---

### 6.2 ISI 0 과 ISI 1 은 대칭이 아니다

**ch0/ch1 은 ISI 1, ch2/ch3 은 ISI 0 을 쓰며, ISI 1 은 넓은 프레임을 단독으로 처리할 수단이 없다.** 원래 설계 기준으로 ch0/ch1 이 불리하다.

#### 근거 — 체인 소유

```dts
isi_chain_buf: isi_chain@32e02000 {   /* ISI 1 의 레지스터 주소 */
    reg = <0x32e02000 0x4>;
};

isi_0 { isi_chain = <&isi_chain_buf>; }   /* ISI 0 만 phandle 보유 */
isi_1 { /* 없음 */ }                       /* m2m_device 도 없음 */
```

```c
/* imx8-isi-core.c:710 */
mxc_isi->chain = syscon_regmap_lookup_by_phandle(dev->of_node, "isi_chain");
if (IS_ERR(mxc_isi->chain)) mxc_isi->chain = NULL;   /* ISI 1 은 NULL */
```

ISI 0 이 넓은 프레임을 처리할 때 **ISI 1 의 라인버퍼를 빌려 쓴다.** ISI 1 은 빌려주는 쪽이라 자기가 넓은 폭을 처리할 수단이 없다.

#### 근거 — 드라이버의 명시적 거부

```c
/* imx8-isi-cap.c:1305 (enum_framesizes), :1358 (enum_frameintervals) */
if (of_device_is_compatible(parent, "fsl,imx8mp-isi") &&
    width > ISI_2K && isi_cap->id == 1)
        return -EINVAL;
```

i.MX8MP 에서 **ISI 1 만** `ISI_2K` 초과 폭을 거부한다. ISI 0 에는 이 가드가 없다.

#### 현재는 우회된 상태다

```c
/* imx8-common.h:66 */
#define ISI_2K		4096U //2048U
```

`git log -S` 확인 결과 이 프로젝트에서 변경한 것이다:

```
51e1d0ddb1d0  youstar02  2023-01-08  "Modify max9296 device driver"
```

`ISI_2K = 4096` 이면 3840 < 4096 이므로:

- `chain_buf()` 가 else 분기를 타서 **체인이 아예 걸리지 않는다** (`chain_buf = 0`)
- `id == 1` 가드도 발동하지 않는다
- 두 ISI 가 각자 3840 을 **체인 없이 단독 처리**한다

30fps 에서 두 채널이 동일하게 동작하는 것은 "제약이 없다" 가 아니라 **"제약이 우회됐다"** 는 뜻이다.

#### 관측된 비대칭

§3.2 매트릭스에서 30fps 는 동일한데 60fps 에서만 갈린다:

| 케이스 | @30fps | @60fps |
|---|---|---|
| A: ch0/ch1 듀얼 3840 (**ISI 1**) | 27.33 | **0 프레임** |
| B: ch2/ch3 듀얼 3840 (**ISI 0**) | 27.33 | 19.80 |

**ISI 1 이 체인 없이 3840 을 처리하는 것이 고부하에서 한계에 걸리는 것**으로 설명될 수 있다. §8.1.1 의 ISI 인터럽트 이상(프레임당 1.4~3.0 회)도 같은 계열일 가능성이 있다.

**단 이는 가설이다.** FHD 60fps 가 안 되는 주된 원인은 AP1302 MIPI 출력(1.2 Gbps)으로 확정됐고 그 값은 두 채널이 동일하므로, ISI 는 **일반적인 fps 상한의 원인이 아니다.** ch0/ch1 만 60fps 에서 완전히 죽는 **국소적 비대칭**을 설명할 후보일 뿐이다.

#### 검증 방법

- **결정적**: `ISI_2K` 를 2048 로 되돌려 커널 재빌드. ISI 0(video3)은 체인으로 3840 을 처리하고 ISI 1(video4)은 `-EINVAL` 로 거부해야 한다. ISI 는 빌트인이라 커널 재빌드가 필요하다.
- **간단**: 3840 스트림 중 `CHNL_CTRL` 의 `CHAIN_BUF` 필드를 `devmem` 으로 읽어 체인이 실제로 꺼져 있는지 확인.

#### 이력 주의

이전 세션(2958c6b2)에서 "ISI 라인버퍼/체인 이론"을 제기했다가 **"완전히 틀렸다"고 철회**한 기록이 있다. 그 철회는 "30fps 3840 이 정상 동작한다"는 관측에 근거했는데, 위와 같이 그것은 우회의 결과이므로 **철회가 과했다.** 구조적 비대칭 자체는 실재한다.

## 7. FHD 60fps 실현에 남은 작업

FHD60 에는 **독립된 관문이 두 종류** 있고, 둘 다 넘어야 한다.

- **(가) 센서 판독 시간** — 한 프레임을 16,667 µs 안에 읽어낼 수 있는가
- **(나) 출력 대역** — 초당 1,990 Mbps 를 내보낼 수 있는가

둘은 별개다. (나)만 풀면 센서가 프레임을 제때 못 내고, (가)만 풀면 대역에서 막힌다. 실제로 (가)만 해결한 상태의 최고치가 26.7 fps 였고, 이는 (나)의 실효 상한(~28 fps)과 일치한다.

**(나) 를 여는 방법은 아직 없다.** 1바이트 패치는 `HINF_MIPI_FREQ` 를 499.2 Mbps 로 바꾸지만 그 설정에서 ISP 출력이 0 이 된다(§4.3-라). 동반 클럭 값이 맞지 않기 때문이며, 어떤 값들을 함께 바꿔야 하는지는 확인하지 못했다. 사실상 **벤더가 정합한 펌웨어가 필요하다.**

### 7.1 필요한 변경 전체

| # | 관문 | 대상 | 현재 값 | 목표 | 적용 방법 | 상태 |
|---|---|---|---|---|---|---|
| 1 | (가) | AP1302 `R0x201C` PREVIEW_LINE_TIME | `0` (자동 → 26.27µs) | **≤ 14.2 µs** (권장 13.0) | 드라이버, 펌웨어 로드 후 | **동작 확인** |
| 2 | (가) | AP1302 `R0x2020` PREVIEW_MAX_FPS | `0x1E00` (30.0) | `0x3C00` (60.0) | 드라이버, 펌웨어 로드 후 | 쓰기 확인 |
| 3 | (가) | AP1302 `R0x6112` TRIGGER_MAX_MISMATCH | `20` µs | `0` (스킵 억제) | 드라이버, 펌웨어 로드 후 | **효과 확인** |
| 4 | (나) | 펌웨어 blob 오프셋 0x11 | `0x2c` (300.0) | `0xf4` (500.0) | 1바이트 패치 | **값은 바뀌나 출력 0** |
| 4' | (나) | blob 의 동반 클럭 값 (PLL·분주비 등) | ? | ? | **벤더 펌웨어 필요** | **미확인** |
| 5 | (나) | MAX9296 `0x0320` (BACKTOP25) | `0x24` | ? | 드라이버 레지스터 테이블 + 재빌드 | **미검증** (4 가 막혀 도달 못 함) |
| 6 | (나) | SoC `csis-hs-settle` | `13` | ? | DTS + DTB 재빌드 + 재부팅 | **미검증** (동상) |

### 7.2 1~3 은 ISP 레지스터이며 런타임 설정 가능하다

펌웨어에 갇힌 값이 아니다. 펌웨어 로드 완료 후 드라이버가 쓰면 그대로 먹는다 — 실측 근거:

| 레지스터 | 실측 |
|---|---|
| `PREVIEW_LINE_TIME` | 15.0 / 14.8 / 14.5 / 13.0 / 12.0 µs 로 쓸 때마다 `SENSOR_LINE_TIME` 이 실제로 따라옴. 13.02µs 에서 `SENSOR_FRAME_TIME` 28,368 → **14,063 µs** |
| `PREVIEW_MAX_FPS` | 30.0 → 60.0 리드백 확인 (단독으로는 fps 변화 없음 — 다른 관문이 남아 있어서) |
| `TRIGGER_MAX_MISMATCH` | 0 으로 두면 FHD@60 19.8 → **26.7 fps**, HD@50 46.0 → **49.8 fps** |

블랭킹 오버헤드가 실측 ~700 µs 이므로 `TOTAL < 16,667` 을 만족하려면 `FRAME ≤ ~15,950 µs` → **라인타임 ≤ 14.2 µs**. 여유를 두려면 13.0 µs 가 적당하다.

적용은 ATOMIC 시퀀스로 묶는다 (드라이버의 기존 패턴과 동일):

```c
/* max9296_s_stream() 의 펌웨어 로드 직후, 0x1186 쓰는 자리 근처 */
ap_write(0x1184, 0x0001);            /* ATOMIC RECORD */
ap_write(0x201C, 0x000D0000);        /* PREVIEW_LINE_TIME = 13.0us (u16.16) */
ap_write(0x2020, 0x3C00);            /* PREVIEW_MAX_FPS = 60.0 (u8.8) */
ap_write(0x6112, 0x0000);            /* TRIGGER_MAX_MISMATCH = 0 */
ap_write(0x1184, 0x0013);            /* ATOMIC FINISH */
```

30fps 이하 모드에서는 기존 동작을 유지하도록 요청 fps 로 게이트를 걸면 회귀 위험이 없다.

### 7.3 5·6 은 런타임 조작으로 대체 불가

- `0x0320` 을 `0x25`/`0x26`/`0x2f` 로 런타임 변경 → 전부 프레임 0. 드라이버는 이 값을 `load_regs` 에서 **CSI 출력을 켜기 전에** 쓴다.
- `csis-hs-settle` 을 `0x32e50024`(DPHYCTRL[31:24]) 직접 쓰기로 4~30 스윕 → 전부 CSI2 이벤트 0. `mipi_csis_set_hsync_settle()` 은 `start_stream()` 안에서 시스템 인에이블 **전에** 적용되므로, 그 뒤에 레지스터만 바꿔도 D-PHY 가 HS 를 재획득하지 않는다.

### 7.4 값을 모르는 이유 (5·6)

- MAX9296 `0x0320[4:0]` = `phy1_csi_tx_dpll_predef_freq`, "CSI PHY1 output frequency in multiples of 100MHz". 리셋 기본값 `0x0F`(=15). 499.2 Mbps 에 대응하는 값이 정수로 떨어지지 않는다.
- `csis-hs-settle` 은 NXP 가 수동 튜닝값으로 두고 있고 (`of_property_read_u32` 로 읽어 레지스터에 그대로 기록), 계산식이 BSP 문서에 없다.

**재빌드·재부팅을 반복하며 조합을 탐색해야 하며 여러 사이클이 걸린다.**

### 7.5 정리

| 관문 | 항목 | 난이도 |
|---|---|---|
| (가) 센서 판독 | 1·2·3 — ISP 레지스터 | **낮음.** 드라이버 코드 몇 줄, 동작 확인됨 |
| (나) 출력 대역 | 4·4' — 펌웨어 blob | **높음.** 값 위치는 찾았으나 단독 변경으로는 출력이 죽는다. 동반 값 미확인 → **벤더 펌웨어 필요** |
| (나) 출력 대역 | 5·6 — 하류 정합 | **미검증.** 4 가 막혀 시험 자체를 못 했다 |

**실질적 난관은 (나) 전체다.** (가)는 런타임 레지스터로 해결되지만, (나)를 열지 못하면 (가)만으로는 26.7 fps 가 상한이다.

정합한 펌웨어를 벤더에서 받으면 그때 5·6 을 탐색하면 된다. 벤더 문의 시 제시할 근거:

- 현재 `HINF_MIPI_FREQ`(R0x0068) = 300 Mbps/lane, 4 lane = 1.2 Gbps
- 필요값 = 498 Mbps/lane 이상 (FHD60 = 1,990 Mbps)
- AP1302 스펙은 4 lane × 1.2 Gbps/lane, 1080p@120fps
- blob 오프셋 0x11 을 단독 변경하면 `HINF_MIPI_FREQ` 는 499.2 로 바뀌고 라인타임도 재계산되지만 ISP 출력이 0 이 된다 → 동반 클럭 값의 정합이 필요하다
- 센서(AR0234)는 라인타임 13 µs 까지 실동작 확인 (60fps 급 가능)
- GMSL 링크(3 Gbps)와 SoC 수신부(4 lane / 500 MHz)는 이미 여유

### 즉시 가능한 대안

**HD 1280×720 @60fps — 55.5 fps 실측.** 펌웨어·드라이버·DTS 변경 없이 현재 상태로 동작한다.

## 8. 재현 절차

도구는 `tools/` 에 있고 보드 `/root/camtest/` 에 배포한다.

| 스크립트 | 스트림 | 계층 | 용도 |
|---|---|---|---|
| `cam_hard_reset.sh` | — | — | 모듈 + CSI2/ISI unbind·bind 하드 리셋. `-s` 서비스 정지, `-S` 기동 |
| `cam_fps_probe.sh` | **직접 띄움** | CSI2 / ISI | "이 해상도·fps 가 되는가" 를 **시험**. `-r` 리셋 후 첫 스트림 보장 |
| `cam_fps_matrix.sh` | 직접 띄움 | CSI2 / ISI | 채널 구성 4케이스 매트릭스 (probe 래퍼) |
| **`cam_fps_stack.sh`** | 관측만 | **센서 / ISP / CSI2 / ISI** | 돌고 있는 스트림을 4계층으로 **진단**. 듀얼 시 카메라별 |
| `cam_fps_watch.sh` | 관측만 | CSI2 / ISI | stack 의 경량판. **i2c 를 전혀 안 건드림** |

핵심 차이는 **스트림을 만드느냐, 관측만 하느냐**다.

- 조건을 지정해 시험 → `probe` / `matrix`
- 병목 위치 찾기 → `stack`
- 장시간 무개입 감시 → `watch` (i2c 트래픽 0, AP1302 응답 불가 상태에서도 동작)
- 파이프라인 물림 복구 → `hard_reset`

### 8.1 gstApp 으로는 ISP 출력 fps 를 못 잰다

gstApp 파이프라인에는 `videorate` 와 caps 협상이 들어 있어 프레임을 복제/폐기해 목표 caps 에 맞춘다. 하류에서 관측한 fps 는 소스의 진짜 레이트가 아니다.

대신 **gstApp 을 그대로 돌리면서** `/proc/interrupts` 를 읽으면 된다:

```bash
/root/camtest/cam_fps_watch.sh -d 30 -i 5
```

```
경과   |  소스fps  전달fps  손실%       ← video4 ch0/ch1
5s     |     29.6     29.6      0
10s    |     29.6     29.4      1
20s    |     29.2     29.2      0
```

- 소스fps = CSI2 IRQ ÷ 2 ÷ 초 (프레임당 2회 실측 확인) → 디시리얼라이저가 MIPI 로 실제 보낸 레이트
- 전달fps = ISI IRQ ÷ 초 → 앱이 실제로 받은 레이트
- 손실% 가 크면 ISI 병목, 소스fps 자체가 낮으면 카메라 측 한계

네 계층을 한 번에 보려면 `cam_fps_stack.sh` 를 쓴다 (§8.1.2).

#### 8.1.1 측정 원리 — 처리량 추정이 아니다

네 계층 모두 **실제 개수 또는 시간값**이며, 계산식에 해상도·비트depth·대역폭 항이 없다.

| 계층 | 계산 | 성격 |
|---|---|---|
| 센서 | `10^6 ÷ SENSOR_TOTAL_FRAME_TIME(µs)` | AP1302 가 보고하는 **프레임 주기** |
| ISP 출력 | `HINF_FRAME_CNT 델타 ÷ 실측 경과시간` | 칩 내부 **프레임 카운터** |
| CSI2 | `csi IRQ 델타 ÷ 2 ÷ 실측 경과시간` | **인터럽트 개수** |
| ISI | `isi IRQ 델타 ÷ 실측 경과시간` | **인터럽트 개수** |

본 문서 §4.1 의 대역폭 환산(`1.2 Gbps ÷ 33.2 Mbit/frame = 36.2 fps`)은 측정값을 **설명하려고 따로 계산한 이론치**이지 측정 방법이 아니다.

경과시간은 `sleep` 값이 아니라 `date +%s%N` 로 실측한다. i2c 읽기에 ~0.27 초가 걸리므로 `sleep` 값으로 나누면 ISP 가 센서보다 빠르게 나오는 물리적으로 불가능한 값이 나온다(실제로 그렇게 나왔다).

**CSI2 의 `÷2` 는 해상도 무관하게 검증됐다** — gstApp 정지 후 video4 로 측정한 원시 비율:

```
1920x1080 @30 :  csi/isi = 2.000  2.000  2.000
1280x720  @30 :  csi/isi = 2.000  2.008  2.008
```

**반면 ISI 의 "프레임당 1회" 는 조건부다.** 고부하 조합에서 깨진다.

4채널 듀얼 2560x720 @60 에서 5초 창 6회 연속 측정 (프레임 수는 검증된 `csi_raw ÷ 2` 기준):

```
        video3 (isi.0)                    video4 (isi.1)
 1회   59 fps, ISI 114.8/s → 1.969        59 fps, ISI 100.6/s → 1.705   IRQ/frame
 2회   59 fps, ISI  85.6/s → 1.446        59 fps, ISI  81.4/s → 1.371
 3회   59 fps, ISI  82.1/s → 1.389        59 fps, ISI  82.3/s → 1.390
 4회   59 fps, ISI 108.9/s → 1.840        59 fps, ISI 117.2/s → 1.983
 5회   59 fps, ISI 101.2/s → 1.701        59 fps, ISI 109.0/s → 1.834
 6회   59 fps, ISI 174.2/s → 2.951        59 fps, ISI 158.6/s → 2.696
```

**프레임 수는 59 fps 로 일정한데 IRQ/frame 이 1.37~2.95 로 흔들린다.** 정수도 고정도 아니므로 **나눠서 보정할 수 없다.** 짧은 구간(20초)만 보면 2.05 로 일관돼 보이지만 길게 보면 위와 같다.

초과분은 정상 프레임 완료가 아닌 다른 이벤트(오버플로, 버퍼 부족 재시도, 체인 동작 등)로 보이나 원인은 미확인이다. 프레임 수 자체는 안정적이므로 **영상 손실은 없고**, ISI 가 여분의 일을 하고 있다는 신호다.

단일 채널에서는 정확히 1회(비율 2.000)였으므로 **듀얼 2560 + 60fps + 4채널** 조합에서만 나타난다.

`cam_fps_stack.sh` 는 원시 비율이 [1.6, 2.4] 를 벗어나면 ISI 값에 `*` 를 붙이고 판정에서 제외한다. **그 구간의 전달 레이트는 ISI 대신 CSI2 열을 본다.**

#### 8.1.2 네 계층 동시 측정

```bash
/root/camtest/cam_fps_stack.sh                 # 자동 채널, 20초
/root/camtest/cam_fps_stack.sh -c both -D      # 두 디시리얼라이저 + AR0234 교차검증
```

AP1302 I2C 주소는 모드에 따라 다르다 (`max9296.c:1966-1969`):

| 모드 | ch0/ch2 | ch1/ch3 |
|---|---|---|
| 단일 (1280x720, 1920x1080) | `0x3c` | `0x3c` |
| **듀얼 (2560x720, 3840x1080)** | **`0x11`** | **`0x12`** |

스크립트는 **subdev 포맷 폭**(≥2560 = 듀얼)으로 판별한다. 드라이버와 같은 기준이다. `0x11` 응답 여부로만 판단하면 스트리밍이 없을 때 AP1302 가 응답하지 않아 듀얼을 단일로 오판한다(실제로 그렇게 틀렸다).

듀얼에서 두 카메라 영상은 하나의 넓은 프레임(2560/3840)으로 합쳐져 전송되므로 CSI2/ISI 는 합성 프레임을 세며, 카메라별 ISP 출력과 **같은 값**이어야 한다. 픽셀이 아니라 프레임을 세기 때문에 스케일 보정이 필요 없다.

실측 예 (듀얼 3840x1080@30, 두 AP1302 를 각각 읽음):

```
평균 | ch0 (0x11) | 센서 30.0 | ISP 29.5 | CSI2 29.3 | ISI 29.5 | 낙차 1.6%
평균 | ch1 (0x12) | 센서 30.0 | ISP 29.5 | CSI2 29.1 | ISI 29.3 | 낙차 1.7%
```

### 8.2 SERDES 상류 프레임 수 세기

```bash
# AP1302 가 실제 내보낸 프레임 수 (8비트 순환)
i2ctransfer -f -y -a 2 w2@0x3c 0x00 0x02 r2   # 상위 바이트 = HINF_FRAME_CNT
```

2초 간격으로 샘플링해 델타를 취하면 AP1302 출력 fps 가 나온다. 같은 구간의 `32e50000.csi` IRQ 델타 ÷ 2 와 비교하면 GMSL 구간 손실 여부를 알 수 있다.

### 8.3 펌웨어 MIPI 레이트 패치

**경고: 이 패치를 적재하면 카메라가 동작하지 않는다.** `HINF_MIPI_FREQ` 는 499.2 Mbps 로 바뀌지만 ISP 출력이 0 이 된다(§4.3-라). 대역 관련 조사를 재개할 때만 쓰고, 끝나면 반드시 원본으로 복구한다.

보드에는 패치본이 `v4l-ap1302-ar0234.fw.mipi500`(md5 `fe68e401f86cbb1c0721d68408b82a0f`) 로 만들어져 있다. 드라이버는 `v4l-ap1302-ar0234.fw` 이름만 로드하므로 덮어써야 적용된다.

```bash
F=/lib/firmware/v4l-ap1302-ar0234.fw
cp -a $F ${F}.orig                       # 원본 백업 (md5 c0830fa0fae6c3c6fecdfd1c84ea9c70)
python3 - <<'PY'
F="/lib/firmware/v4l-ap1302-ar0234.fw"
d=bytearray(open(F+".orig","rb").read())
assert d[0x10]==0x01 and d[0x11]==0x2c
d[0x11]=0xf4                             # 300.0 -> 500.0
open(F,"wb").write(bytes(d))
PY
/root/camtest/cam_hard_reset.sh -s       # 모듈 재로드 -> 다음 스트림에서 펌웨어 재로드
```

복구:

```bash
cp -a ${F}.orig $F && /root/camtest/cam_hard_reset.sh -s -S
```
