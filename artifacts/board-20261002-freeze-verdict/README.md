# 듀얼와이드 360p120 동결의 `pair` 판정 — 실기 측정

이슈 #65 가 요구한 "현장 증거 확보 수단"(쌍의 HINF 가 벌어지거나 한쪽이 정지할 때
change-only 로 상태를 남기는 것)이 실기에서 동작하는지, 그리고 **실제 동결이 어떤
판정으로 찍히는지**를 측정했다.

## 환경

| 항목 | 값 |
|---|---|
| 보드 | `pim` (i.MX8MP, max9296 4ch) |
| 커널 | `5.10.35-lts-5.10.y+g2fce14defc04` |
| 적재 모듈 | srcversion `00FEDDF6CFD9B1C1F2F0E6B` (source `f6230c5`) |
| 재현 프로브 | gstApp `test/probe-freeze-repeat.sh`, sha256 `6d0d161c…cf06` |
| 프로브 설정 | `SAMPLES=90 ROUNDS=4`, `IVL_MS=1000`, 통제 `exp=2000 bps=4096` |
| 시험 config | `.VHL_CAM.cam_width=640 cam_height=360 fps=120` (프로브가 씀) |
| 운영 config | 1280x720@15, md5 `8cb2eae2ac4c1f2fa6f3ca831d6758b4` (측정 후 복원 확인) |
| 소비자 | `camera-max9296-health.service` 수동 기동, `--interval-ms 1000` |

프로브 셀은 교차 배치된다 — A: ch0+ch1 통제, B: ch2+ch3 통제, C: ch0+ch1 운영값
(led_flash 만 4채널 off). ch0/ch1 은 i2c2, ch2/ch3 은 i2c1 에 보인다.

## 무엇을 물었나

1. 이 보드의 모듈이 `pair` 판정을 **계산할 수 있는가** — 0 건이 "없음"인지 "계측
   불가"인지 구분하기 위한 양성 대조.
2. 1Hz 소비자가 판정 가능 구간 안에 들어오는가.
3. **실제 동결이 어떤 판정으로 커널 로그에 남는가.**
4. 1Hz 소비자를 추가하는 것이 현상을 억제하는가 (관측자 교란).

## 양성 대조 (측정 전)

| 확인 | 결과 |
|---|---|
| `pair` 필드 존재 | 두 버스 모두 `"mode":"dual-wide"`, `"streaming":true`, `"pair"` 존재 |
| 분류기 생존 | 냉시작 1회 읽기에서 `"sample_gap_ms":18785` → 상한 초과로 `NOT_APPLICABLE`. 코드 부재가 아니라 **간격**이 사유 |
| 1Hz 가 판정 가능 | 1008 ms 간격 두 번째 읽기에서 `NOT_APPLICABLE` → `ALIGNED` |

### `BOTH_STALLED` 를 동결로 읽으려면 지속을 봐야 한다

`BOTH_STALLED` 는 **스트림 시작 직후 1 샘플짜리 과도 상태로도 나온다.** 이 측정에서
세 번 나왔고(회차 8 의 시작, 그리고 측정 종료 후 `cam-operate` 가 되살아날 때 두 버스
각각), 셋 다 1~2 읽기 만에 `ALIGNED` 로 복구했다. 구별은 선행 판정과 지속으로 된다.

| | 선행 판정 | 이후 |
|---|---|---|
| 동결 (4/4) | `ALIGNED` 또는 `DIVERGENT` | 복구하지 않는다 |
| 시작 과도 (3/3) | `NOT_APPLICABLE` | 1~2 읽기 안에 `ALIGNED` |

이 표본에서 둘은 겹치지 않았다. classifier 가 baseline 재시드 뒤 `BOTH_STALLED` 를
강제하는 것은 아니지만, 관측된 과도 셋이 모두 스트림 시작 구간이었으므로 **단일 샘플로
경보하는 소비자는 스트림 재기동에서 오경보할 수 있다** — 이 측정에서는 `cam-operate`
재기동이 그 경우였다. n 이 작으므로 "선행이 `NOT_APPLICABLE` 이면 항상 과도"로도,
"재기동하면 항상 나온다"로도 일반화하지 않는다.

### 회차와 판정 줄을 어떻게 묶었나

`dmesg -w` 를 측정 시작 전부터 파일로 받았다(이 저장소의 cable 회차 기록에 커널 로그를
회전으로 잃은 전례가 있다). 묶는 근거는 셋이고, 셋이 서로 독립이다.

1. **uptime ↔ 벽시계**: 측정 중 `date -u` 와 `/proc/uptime` 을 같이 찍어 기준점을 잡고,
   프로브 로그 헤더의 벽시계로 런 시작 uptime 을 환산했다.
2. **i2c 인스턴스 ↔ 셀의 채널**: A·C 는 ch0/ch1(i2c2), B 는 ch2/ch3(i2c1). 12 회차
   **전부** 일치했다.
3. **동결/완주 ↔ 정지/무정지**: 12 회차 **전부** 일치했다. 완주 8 회차에는 정지 판정이
   하나도 없고, 동결 4 회차에는 모두 있다.

### `seq=` 가 단일 1Hz 독자를 확증한다

`seq` 는 장치별 `health_raw` 읽기 순번이다.

| 회차 | 판정 줄의 seq / uptime | 읽기 수 / 경과 |
|---|---|---|
| 1 | `seq=13` @15150.68 → `seq=16` @15153.73 | 3 / 3.04 s |
| 4 | `seq=13` @15501.72 → `seq=25` @15513.87 → `seq=30` @15518.93 | 12 / 12.15 s, 5 / 5.06 s |

읽기 간격이 1 초다. 프로브의 `capapp` 은 `health_raw` 를 열지 않는다(`strings` 로
확인 — `prepare`, `enable`, `rotate`, `link_status` 만 나온다). 따라서 공유 baseline 의
유일한 소유자는 1Hz 소비자였고, `sample_gap_ms` 가 의도한 1 초였다.

## 결론

### 1. 현장 증거 경로는 동작한다

실제 동결 4/4 가 커널 로그에 change-only 로 남았다. 이슈 #65 본문이 "원인 해결이 아니라
현장 증거 확보 수단"으로 제시한 것이 이 보드에서 성립한다.

### 2. `BOTH_STALLED` 도 동결의 서명이다 — 두 판정을 함께 봐야 한다

4 건 중 3 건은 `DIVERGENT` 를 거치지 않고 바로 `BOTH_STALLED` 로 들어갔다. 남은 1 건
(회차 4)은 `DIVERGENT` 가 **약 5 초 지속**한 뒤(seq 25 → 30, change-only 이므로 그 사이
seq 26–29 도 같은 판정) `BOTH_STALLED` 로 넘어갔다.

따라서 동결에는 두 양상이 있다.

- **동시 정지** (3/4): 두 채널 HINF 가 같은 1 초 창 안에서 멈춘다 → `BOTH_STALLED` 직행.
- **순차 정지** (1/4): 한쪽이 멈추고 다른 쪽이 수 초 더 돈다 → `DIVERGENT` → `BOTH_STALLED`.

HINF 는 채널별 ISP 출력이므로 두 양상은 "한쪽 ISP 만 멈췄나"로 갈리는 것으로 보인다
(추정).

**`DIVERGENT` 만 감시하는 소비자는 이 표본에서 4 건 중 3 건을 놓친다.** 거꾸로도
성립하지 않는다 — `max9296_pair_health.h` 머리말이 기록한 포착
(`poll_20260907_120018_slow_t7`)은 ch B 의 HINF 가 **36 초** 고정된 채 ch A 가 계속
진행한 경우로, **지속된 `DIVERGENT`** 다. 즉 `DIVERGENT` 를 과도 상태로, `BOTH_STALLED`
를 지속 상태로 나누는 것은 틀렸다. **둘 다 서명이고 함께 봐야 한다.** 관측된
`DIVERGENT` 지속은 이번 약 5 초와 그 포착의 36 초이고, 나머지 3 건은 이 판정 없이
`BOTH_STALLED` 로 직행했으므로 판정이 얼마나 오래 유지되는지로 양상을 예측하지 않는다.
**1 초보다 짧은 `DIVERGENT` 는 관측하지 않았다** — 직행한 3 건이 짧은 한쪽 정지를
지났는지 두 채널이 정말 동시에 멈췄는지는 1 초 해상도로 갈라지지 않는다.

### 3. 1Hz 소비자는 현상을 억제하지 않는다

프로브의 1 초 레지스터 판독 위에 `health_raw` 1Hz 판독을 **더한** 조건에서 동결이
4 건 발생했다. 양성 발생이므로 비율 비교 없이 결론이 선다.

### 4. 동결은 스트림 시작 직후에 몰린다

4 건이 +1.0 / +2.0 / +3.0 / +12.0 초다. 이슈 #65 에 기록된 기존 3 건은 15 / 27 / 34 초이고,
따라서 **관측된 7 건 전부가 ≤34 초**다. 발생률만 다시 재려면 90 초 창이 필요하지 않을
수 있다 — 다만 프로브 헤더의 논거("40 초 창으로는 *안 언다* 와 *아직 안 얼었다* 가
구분되지 않는다")는 **"안 언다"를 입증하려는 목적에는 그대로 유효하다.** 창을 줄이는
것은 발생률 측정에만 해당한다.

### 5. ~104 fps 센서 고정이 재현됐다

4 건 모두 최소 한 채널이 104 fps 대에 고정됐다. 이슈 #65 의 기존 확정 사실과 같다.

## 이 측정이 주장하지 않는 것

- **원인을 밝히지 않았다.** 왜 HINF 가 멈추는지, 왜 센서 프레임시간이 104 fps 대에
  고정되는지는 그대로 미해결이고 벤더 답 대기 항목이다.
- **셀 C 의 0/4 를 노출 효과로 돌리지 않는다.** 프로브 헤더는 C 를 선행 실패가 관측된
  조건으로 적었는데 이번에는 4 회 모두 완주했다. 그러나 이슈 #65 는 노출만 바꾼 15 회차로
  "노출 의존성 — 확인되지 않음"을 이미 결론으로 적었고, C 는 A·B 와 노출 외에 bps 와
  led_flash 도 다르다. n=4 에 교란 변수가 둘 이상이므로 **철회된 가설을 되살릴 근거가
  아니다.**
- **동결율 4/12 를 이슈의 slow 갈래 1/10 과 직접 비교하지 않는다.** 창 길이가 90 초 대
  60 초로 다르다.
- **두 양상의 비율(3:1)을 일반화하지 않는다.** n=4 다.
- **`DIVERGENT` 가 왜 3 건에서 안 나왔는지의 메커니즘을 확정하지 않았다.** 한쪽-정지
  구간이 1 초보다 짧았을 수도 있고 두 채널이 정말 동시에 멈췄을 수도 있다. 이 측정의
  해상도(1 초)로는 갈라지지 않는다. 회차 4 에서 센서 고정값이 유일하게 비대칭
  (`104.6|59.0`)이었던 것이 순차 정지와 **양립하지만**, n=1 이므로 상관을 주장하지
  않는다 (추정).
- **느린 전달 조건을 재현하지 않았다.** `docs/health-raw-v1.md` 의 호스트 측정 표는
  실전달이 설정의 절반 아래인 경우를 다루며, 이 측정은 그 조건이 아니다. 두 결과는
  서로 다른 사유로 같은 오독(`DIVERGENT` → `BOTH_STALLED`)에 이른다.

## 측정 중 발견한 도구 결함 2 건

둘 다 측정 자체와 무관하게 다음 사람에게 영향을 준다.

1. **보드의 `probe-freeze-repeat.sh` 가 구버전이었다.** 생산자 입력
   (`/root/shared_v/edgeconf_pim.json`)에 시험 config 를 쓰는 판이어서, `cam-operate` 를
   멈춘 채 도는 이 프로브에서는 **반영되지 않는다**(gstApp 이슈 #113). 그대로 돌렸으면
   120 fps 시험 config 없이 90 초를 완주하고 "동결 없음"을 보고했을 것이다 — 오음성이다.
   저장소 수정본을 배포하고 해시 일치를 확인했으며 구버전은 보드에 보존했다.
2. **`pim_runtime.orig.json` 백업이 live 와 달랐다.** 백업에 `NETWORK.ETH1.*` 키가
   없었다(확정). 프로브는 측정 후 백업 내용으로 복원하므로, `ALLOW_CONF_DRIFT=1` 로
   진행했다면 그 운영 키들이 사라졌을 것이다. live 로 갱신하고 낡은 백업을 보존했다.
   백업의 `exp_time` 이 프로브의 통제값과 같았던 점은 백업 자체가 시험 조건 중에
   떠졌을 가능성을 시사하지만 단정하지 않는다 (추정).

## 인용 방식

고정 줄번호와 고정 개수를 쓰지 않는다 — 인용 대상이 살아 있는 파일이어서 조용히
거짓이 되고, 그것을 잡아 줄 테스트가 없다. 위에 적은 개수는 **이 측정의 관측값**이지
저장소 상태가 아니다.

## 원시 기록

`artifacts/board-*/raw/` 는 추적하지 않으므로, 판정 증거는 위 "판정 줄 전문" 표가
전부다 — 런 구간 18 줄의 uptime·장치·판정·이전 판정·`seq`·`held`·HINF 쌍이 그 표에
있다. 그 밖에 재현에 필요한 것은 환경 표(프로브 이름·해시·환경변수, 시험/운영 config),
셀 구성, 회차별 결과 표, 묶는 근거 셋이다.

**이 저장소가 담지 않는 것**은 회차별 원시 시계열이다 — `csi_d`/`isi_d`/`a_dhinf`/`a_sfps`
열을 가진 프로브 CSV 와 `dmesg -w` 전문은 보드의 `/root/fpsmeas/` 에만 있다
(`freeze_<stamp>.{log,csv}`, `freeze_<stamp>_summary.csv`, `dmesgw_<stamp>.log`). 위
표들은 그 시계열에서 판정과 요약만 뽑은 것이고, 시계열 자체로 다시 확인하려면 보드
원본이나 이슈 #65 의 측정 코멘트를 봐야 한다.
